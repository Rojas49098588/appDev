## Repository state

The repository root contains standalone scratch files with no build system connecting them:

- `test.py` — standalone Python script, run directly with `python test.py`
- `test.java` — standalone Java file defining `public class test`; run with `javac test.java && java test`

## mobile-app/ (Expo React Native app)

`mobile-app/` is a separate Expo project (TypeScript, blank template) targeting Android and iOS. It runs on Expo SDK 58 (pinned to match the Expo Go app version available for testing on-device — see `mobile-app/AGENTS.md`, which points to versioned Expo docs that must be checked before writing Expo code, since the API surface has changed across versions).

Commands (run from `mobile-app/`):
- `npm start` — start the Expo dev server (Metro + QR code for Expo Go)
- `npm run android` — start with the Android target
- `npm run ios` — start with the iOS target (requires macOS to build; use Expo Go otherwise)
- `npm run web` — start the web target
- `npx expo-doctor` — validate the project setup
- `npm test` — unit tests for the pure `lib/` modules (Node's built-in test runner, `tests/*.test.ts`)
- `npm run test:rls` — security-rule tests; ALWAYS runs against the TEST project (`supabase/.env.test.local`)
- `npm run db:apply` — apply `supabase/schema.sql` and `supabase/seed.sql` to the LIVE project (`supabase/.env.local`)
- `npm run db:apply:test` / `npm run db:check:test` — apply (schema + seed + `test-seed.sql`) / check the TEST project
- `npm run test:members -- <csv>` — create TEST-project member accounts for the member rows of a roster CSV (refuses to run if the test URL equals the live URL, or if the live URL can't be read)
- `npm run start:test` — start Expo against the TEST project, using `mobile-app/.env.test.local` (template `mobile-app/.env.test.example`; git-ignored; anon key only)

Entry point is `index.ts` → `App.tsx`. Config (app name, icons, platform-specific settings) lives in `app.json`.

### Data and backend

- Data (accounts, flags, combos and their photos, the current game) lives in Supabase. The schema is `mobile-app/supabase/schema.sql`; starting data is `mobile-app/supabase/seed.sql`.
- Row-level security (RLS) is the only access control: the app talks to Supabase directly with the anon key. After any schema change, `npm run test:rls` must pass.
- The contexts in `mobile-app/context/` render their `mustang.cache.*` AsyncStorage cache first, then fetch from Supabase and subscribe to Realtime. They refetch on reconnect and whenever the auth session is refreshed (`sessionVersion` in `AuthContext`), and skip fetching while there's no live session so the cache isn't overwritten with empty anon results.
- Secrets (service-role key, DB URL) live in `mobile-app/supabase/.env.local`; the app's config (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`) lives in `mobile-app/.env.local`. Both are git-ignored; templates are the matching `.env.example` files. Never put the service-role key in app code.
- Two Supabase projects: live (`supabase/.env.local`) and test (`supabase/.env.test.local`, template `supabase/.env.test.example`). Commands (from `mobile-app/`): `npm test` (pure `lib/` unit tests), `npm run test:rls` (security rules, test project only), `npm run db:apply` (schema + `seed.sql`, live), `npm run db:apply:test` / `npm run db:check:test` (test). `seed.sql` is the invite code plus one placeholder current game ('TBD'); `test-seed.sql` holds sample combos and is applied to the test project only.
- Email change is read-only in the app until custom SMTP is set up.
- Inventory lives in the database: `piece_types` (name, colors, etc.) and `pieces` (one row per physical piece, with its number, color and out-for-repair state). Both are readable by signed-in users, writable by staff only, and in Realtime. Inventory starts empty (no seed); the spreadsheet import (below) or the add-inventory screens create it. `context/InventoryContext.tsx` (`useInventory`) follows the cached-list + Realtime pattern; `lib/inventory.ts` holds the pure helpers (assignment, unknown numbers, table rows, per-type counts). `constants/inventoryData.ts` is gone.
- Member numbers live in `profiles.numbers jsonb`, keyed by piece type name (e.g. `{"Coats":"185"}`), and change only through the staff-only `set_member_numbers(target, new_numbers)`; `guard_profile_update` blocks direct edits. One active member per type + number: a clash raises 23505 "already belongs to" (only new or changed keys are checked). A number with no matching piece is allowed and shown as an amber note on the member plus a warning line in Inventory. The old `coat_size`/`vest_size`/`bibber_size`/`pant_size` columns and `set_uniform_sizes()` are dropped; the migration copied old sizes into `numbers` and raises notices for duplicates. `lib/uniform.ts` has `numberFor`/`matchesNumber`/`digitsOnly`.
- Staff Inventory shows Assigned / Unassigned / Out for repair with filters; "See every {type}" opens `PieceTableScreen` (route `PieceTable { pieceTypeId }`). Staff toggle Out for repair on `PieceHistoryScreen`. Members see every non-retired numbered type that has at least one piece (counted types like ties/belts excluded), with their own number or '—', plus the white shirt.
- Flags are history: a flag row is never deleted. Staff clear it through `clear_flag()` (records who and when); there is at most one open flag per member/piece/color. Members submit through `submit_flag()`, not a direct insert. Staff can edit a flag's color/note (staff edit policy + guard triggers). `staff_note` is readable by the flag's member (flags_select returns all columns), so it is not secret. `submit_flag(..., p_keep_photo)` lets the server keep the open row's photo (a stale client cache can't clobber or share a cleared row's file). Photos are optional and live in the private `flag-photos` storage bucket under `<member id>/`. `FlagsContext.flags` is open flags only (what My Inventory and the staff chips use); `history` is every flag, open and cleared. `PieceHistoryScreen` (route `PieceHistory`) shows a piece's history, reached by tapping any size chip in staff Inventory (chips are tinted when they have an open flag). `archive_member()` keeps a member's flags.
- Archiving: staff call `archive_member()` (snapshot, including `numbers`, into `member_archives`, clear `numbers` but keep flags (the snapshot holds open flags only), set `archived_at`, ban the auth user for 100 years and delete their sessions) and `restore_member()`. Use a real date for `banned_until`, never `'infinity'`, because Supabase Auth can't parse it. Archived accounts are hidden from the Members tab, and an archived user who is still signed in is signed out by `AuthContext`. Snapshots are viewed on `ArchivedMembersScreen` / `ArchivedMemberScreen` (linked from staff Home).
- Numbers are digits only, with leading zeros stripped (`'085'` -> `'85'`, `'0'` stays `'0'`) wherever they are written: `normalize_number()` / `require_number()` in the schema (non-digits raise 22023) back `set_member_numbers`, the import, `create_piece_type` and `add_piece_number`. Migrated live values may still hold leading zeros, so the duplicate-number check in `lib/` compares with zeros stripped. `schema.sql` also runs a re-runnable `normalize_member_numbers()` that strips the zeros from existing `profiles.numbers` (it runs on live at the next `db:apply`), and `apply_member_numbers` and the import preview compare normalized values.
- Pieces: the `pieces_check_type` trigger rejects a piece whose type isn't numbered or whose color isn't one of the type's colors (22023).
- Importing and adding inventory is staff only, through security-definer functions (no direct writes): `import_inventory(payload jsonb)` (one transaction, a merge that never deletes pieces or clears numbers; re-running the same payload changes nothing; returns counts typesCreated/piecesAdded/markedOutForRepair/numbersSet/notesAdded), `create_piece_type(name, kind, colors, numbers, stock)`, `add_piece_color(type, color)` (adds the color for every existing number; a duplicate color raises 22023 "{color} is already a {type} color") and `add_piece_number(type, number, colors)`. A number always creates a piece in every color of its type.
- Spreadsheet import: pure code in `lib/import/` (`csv.ts` parser, no CSV library; `rows.ts` classifies rows; `preview.ts` matches names and builds the plan/payload), UI in `screens/ImportInventoryScreen.tsx` (route `ImportInventory`, file picked with `expo-document-picker`), reached from the Inventory "+" sheet (`components/AddInventorySheet.tsx`), which also opens `AddPieceTypeScreen`, `AddColorSheet` and `AddNumberSheet`. CSV columns (case-insensitive header): `NAME`, `Section`, `M/F`, `Coat #`, `BIBBER #`, `VESTS`, `Repairs`; `Section` and `M/F` are not imported. `Coat #`/`BIBBER #`/`VESTS` map to the types `Coats`/`Bibbers`/`Vests`, which the import creates if missing with default colors (Coats Blue/Red/Purple/Candy, Vests Candy/Red, Bibbers Blue/White); the names must be exactly these. Row kinds: member (`Last First`, `First Last` also matches; archived, unmatched and ambiguous names are listed and skipped), Addison Sew (Section or NAME contains "addison sew"; the number sits under one piece column and the color in `Repairs`, and that one piece is marked out for repair), `Unassigned` (pieces the band owns that nobody has), blank rows ignored. Line numbers in problems are spreadsheet row numbers (header = line 1). A sheet number is added only when no piece of that type + number exists in any color. When a member's sheet number differs from their app number, staff pick "Sheet" or "App" per row; a member with no current number always gets the sheet number. Numbers that would give two active members the same type + number are listed and skipped. The confirm dialog splits numbers into "new" and "replace an existing number".
- Imported repair notes: a Repairs note on a member row becomes an open `flags` row on every color of that member's coat number (the number as it will be after the import), `source = 'import'`, `member_id` null (so members can't see it; only staff, shown as "from spreadsheet" on `PieceHistoryScreen`) and `member_name` = `first last`. A note already imported for that member name + piece type is left alone on re-runs, even if the text changed. A note with no usable coat number is listed as a problem and skipped.
- `InventoryContext` exposes the writers (`importInventory`, `createPieceType`, `addPieceColor`, `addPieceNumber`) and batches Realtime updates. Number ranges in the add-type/add-number forms are inclusive, start > end is an error, and expansion is capped at 1000 numbers.
- Realtime reload rule (`lib/realtime.ts`): Realtime can drop events in a burst and never replays them, so `InventoryContext` calls `reload()` instead of merging when a flushed piece batch has more than 50 events (and cancels the pending batch), and every channel's status callback (`logChannelFailures(label, onReload)`) reloads on CHANNEL_ERROR / TIMED_OUT and on any SUBSCRIBED after the first. `AuthContext` does the same for the profiles channel and exposes `refreshAccount()`, which the import screen calls after a successful import.
- Test accounts for trying the import on a phone: `npm run test:members -- <csv>` then `npm run start:test` (TEST project only).
- Setup steps for a new Supabase project are in `HANDOFF.md` → Supabase setup.

### Combos and the Catalogue

- Tapping a tile on the staff Catalogue tab (`screens/CatalogueScreen.tsx`) opens `screens/ComboDetailScreen.tsx` (stack route `ComboDetail`, param `{ comboId }`): name + sub-label, enlarged photo, component chips, side-by-side "Set for pregame" / "Set for halftime" (via `useGame().setCombo`), and a Delete button.
- A combo currently assigned to pregame or halftime can't be deleted — member `GameDayScreen.tsx` looks combos up by id from `GameContext`, so deleting one in use would leave Game Day pointing at nothing.
